# D1 读取额度诊断（2026-10-09）

调查对象：exusiai-stat；源码基线 c86d243。只读生产聚合计数、查询分析与 EXPLAIN；未读取身份/凭证/逐局 payload，未改线上代码、架构或套餐。截图的 6.68M 是账户统计（包含两库），下表为本库最近滚动24小时，不应直接作为该截图整个时间窗的精确分解。

## 已确认的主要原因

新版逐局统计 SQL 的 `candidates` / `selected` CTE 被 SQLite 展开。同一局的 `standard_win`、`extended`、`max_act` 在关联多张卡牌时反复执行相关子查询，即使使用索引也重复读取同一批行。生产 `EXPLAIN QUERY PLAN` 显示多个重复的 `CORRELATED SCALAR SUBQUERY 3/4`，分别查询 entities 与 cohort_mods/mod_catalog。

D1 按扫描行数计量，查询次数和返回条数均不能代替读取行数。生产库当前82局、7100条entities、1450条cohort_mods、505条mod_catalog、4局v2、294条card_offers、7份筛选快照。

`wrangler d1 insights --time-period 1d --sort-type sum --sort-by reads` 查询分析：

|查询用途|执行次数|报告平均扫描行数|报告累计扫描行数|
|---|---:|---:|---:|
|旧局逐幕奖励选牌|18|147275|2650956|
|卡牌选择后胜率去重|13|67748|880731|
|旧局获取/升级/删除|4|219919|879678|
|终点持有胜率|4|170672|682688|

四条合计5094053行，足以超过整个账户每日500万行的免费额度。旧版预聚合查询 `cohort_entities` 平均3910行，87次共340231行。查询次数没有大量增加也能超额，主要证据指向SQL重构引入的重复扫描；该报告不能排除其它访问来源，不能据此认定攻击或精确计算全部账户用量。

## 当前读取与缓存逻辑

1. 页面初次打开、点击刷新、应用筛选、可见页面每15分钟均请求 `/api/stats`。卡牌搜索、排序、平铺/列表、升级预览与详情切换均在现有数据上完成，不触发统计重算。
2. Worker 按规范化完整筛选组合建缓存键。当前边缘节点的Cache API命中且结果未满15分钟时返回缓存，无D1查询。
3. 边缘缓存未命中或旧结果过期时读取D1 `snapshots`。同组合D1快照未满15分钟时仅读取该快照；跨边缘请求不会仅因边缘冷缓存而必然重新计算全部统计。
4. 无快照或已过期时执行calculate：9条batch读查询及1条额外去重查询，然后写快照与淘汰记录。各筛选组合独立更新，不是全站每15分钟只重算一次。
5. 定时任务每15分钟强制计算默认组合，且同时分批更新Steam标签。默认快照即使刚由访客生成，定时任务仍可再次计算；没有共享重算锁，多个并发请求也可能重复计算。
6. 数据库失败时可返回旧快照，但旧updated_at保持不变。没有失败冷却，之后的请求可能继续尝试计算。统计API未设置类似上传API的限流。
7. 上传每局也会执行索引查询和写入/聚合更新；Steam标签查询也会读D1。但当前查询分析的主要消耗集中在上述四条统计SQL。

## 本地验证（不是生产性能承诺）

独立Miniflare D1，82条合成对局、7100条合成entities、1450条Mod关系、505种Mod、4局有v2元数据。执行相同查询，然后仅将两层CTE设为 `AS MATERIALIZED`。四条查询的返回结果逐字节一致：

|查询|原读取行数|物化后读取行数|
|---|---:|---:|
|逐幕奖励选牌|1260291|31587|
|获取/升级/删除|162286|28267|
|终点持有|374932|32037|
|选择后胜率去重|633187|38806|

这是验证“重复求值”原因的最小实验，未加入生产代码。单纯物化仍不足以保证每天96次、多筛选组合、数据增长后的总成本低于免费额度；不能作为最终修复。

## 建议的修复顺序

- 首先去掉重复相关子查询：每局幕数/胜负/扩展幕判断只计算一次，按局关联汇总；新局持久化可稳定的结算信息，Steam标签变动时针对关联环境更新。避免CTE携带未使用payload等字段。
- 恢复增量预聚合并扩展至v2指标：上传时增量更新，可加总的统计不再每次从原始明细扫描。保留原始明细用于校验/未来分析。
- 把统计重算与公共请求分离：定时任务统一发布统计代次，访客及自定义筛选基于缓存的汇总资料处理；不直接向公众暴露无限组合的明细重算入口。具体缓存存储需按免费配额、汇总大小和筛选计算CPU实测选择。
- 加共享重算锁、定时任务与请求去重、失败冷却和有界的请求限流；刷新只读最近成功结果。为每次计算记录不含身份/参数/payload的阶段、耗时、meta.rows_read、缓存状态，设置每日读取预算。
- 性能回归必须覆盖旧局、v2、混合局、多Mod、各种幕范围与升级拆分，验证结果等价，并验证按96个更新时间窗、常用筛选和预期数据增长计算的总成本。只延长缓存或追加索引不能视为完成。

免费每日额度在00:00 UTC（北京时间08:00）重置。
