# 对局数据存储与性能评估

本文记录存储候选方案、验证方法和迁移条件。

## 数据结构与查询需求

对局共享外层格式和字段语义，但并非完全相同的平面记录：旧局缺少详细数据，新局包含逐幕卡组、选牌、物品和战斗等变长数组，并有可选的基准字段。迁移时必须保留格式版本和缺失值语义，不能把缺失数据补成零。

常用筛选字段应独立保存为可索引的列，例如日期、进阶、模式、人数和内容版本。详细事实按局保存，先筛选再解码；计算结果继续复用缓存，不能让每个访问请求重新解压全量对局。有新数据时才换版，两次统计换版至少间隔15分钟；迁移须保留这一行为。

单纯把原样 JSON 移到另一张表不会压缩内容，还会增加关联键等开销。减少重复字段、共享字符串字典、二进制编码及通用压缩才有实质空间收益。

## 本机测试，2026-10-11

样本为 305 个真实对局；另复制为 3,050 局，仅用于增加计算量，不代表内容多样性的增长。采用实际指标贡献和合并函数，逐局读取，独立进程预热后测量三次，取中位数。各方案的指标输出完全一致。

测试库只包含事实内容、序号、进阶及相同进阶索引，不含完整业务元数据、Mod 目录或 WAL；因此文件大小不能直接当作最终迁移库的大小。峰值 RSS 是整个测试进程的内存，不是解压器单独占用。

| 原始 JSON | 5.02 MiB | 1.27 秒 | 190 MiB |
| SQLite JSONB | 4.39 MiB | 1.17 秒 | 191 MiB |

3,050 局时，原始 JSON 与逐局 gzip 等级 6 的文件分别为 50.17 / 9.00 MiB，全量计算为 14.73 / 14.61 秒，峰值 RSS 为 205 / 204 MiB。筛选 A10 后计算 940 局，耗时为 4.51 / 4.66 秒。

只进行读取、解压和解析时，3,050 局的原始 JSON / gzip 耗时约 250 / 335 毫秒，峰值 RSS 约 61 / 78 MiB。完整流程中，指标聚合约占 96% 的耗时，成为主要性能和临时对象内存开销。不能把磁盘压缩率理解为运行内存的减少。

逐局纯编码对比中，gzip 等级 6 / Zstd 等级 3 的内容合计约 705 / 767 KiB；305 局解压并解析约 26 毫秒。该微测试不包含完整 SQL 和聚合开销。

## 远端一次性测试，2026-10-11

使用同一份 305 局快照，隔离运行，未修改业务数据。当前规模每项预热后测量三次；3,050 局复制压力样本每项单次运行，主要用于发现数量级瓶颈，不用于精确排名。测试采用统一 CPU 和内存限制，文件系统缓存未清空，不能据此推断冷盘吞吐。

CPU 时间表示实际消耗，墙钟耗时还包括配额等待等。RSS 为计算进程峰值；隔离测试整体峰值还包含文件缓存等。峰值覆盖启动和预热，不能等同于单独解压开销。这里测量读取、解析和指标贡献合并，不包含输出组装、完整访问、结果缓存和并发上传链路；预热也不复用应用统计结果，不能把重算耗时当作每次访问的响应时间。

## 最终选择

**推荐逐局 gzip 等级 6，作为磁盘空间优化，不作为内存优化或计算提速手段。** 当前规模耗时和 CPU 成本与原始 JSON 接近，压力样本的进程内存增加约 4 MiB，没有出现明显计算成本放大。相比之下，JSONB 空间收益较小；分块方案牺牲单局操作便利；无字典 Zstd 虽编码更快，存储稍大，尚无足够收益需要改用它。

3,050局时，原始 JSON 和逐局 gzip 全量计算均约76秒；聚合占绝大多数时间。后续应先优化重复创建、合并和排序聚合对象的逻辑，不能靠更换压缩格式解决交互查询的扩展问题。该结论不保证在更多独立玩家、更多字段或更大内容多样性下仍保持相同内存水平。

本轮完成实验和方案选择，尚未迁移业务数据。压缩本身不减少业务写入行数；重复的 Mod 目录更新需独立优化。迁移前应统一所有事实解码路径，覆盖筛选统计、基准重建、Mod使用计数、导入导出和校验，再做完整链路回归。

## 候选方案

| 方案 | 优点 | 代价与适用场景 |
| --- | --- | --- |
| 普通索引列＋逐局 gzip BLOB | 约八成测试库空间收益；单局独立、实现简单 | 需要解压才能访问详细字段；优先候选 |
| SQLite JSONB | 保留 SQLite 的 JSON 查询功能，减少数据库内部解析 | 本次空间收益约 13%；JS 计算仍需转换、解析，不是通用压缩 |
| 逐局 Zstd | 快速压缩；可使用共享字典消除跨记录重复 | 本次无字典压缩未胜过 gzip；字典需要训练、版本化和长期保留 |
| 分块压缩 | 可以利用相邻对局的重复内容 | 单局筛选、更新与去重更复杂；块级索引和未压缩尾部需要设计 |
| Avro | schema 与记录分离，避免反复存字段名；支持块压缩和格式演进 | 适合归档和交换；仍需配套查询工具，本次未实测 |
| Parquet＋DuckDB | 列式压缩、嵌套字段、列裁剪和筛选下推 | 适合大量历史数据的批量分析；需要重写分析流程并验证内存，本次未实测 |

资料：[SQLite JSONB](https://sqlite.org/jsonb.html)、[Zstd 与字典](https://facebook.github.io/zstd/)、[Avro 规范](https://avro.apache.org/docs/1.12.0/specification/)、[Parquet 设计](https://parquet.apache.org/docs/overview/motivation/)、[DuckDB Parquet 查询](https://duckdb.org/docs/current/data/parquet/overview)。

## 迁移验证清单

1. 使用一致快照制作副本；记录样本量、格式版本和缺失字段覆盖情况。
2. 比较完整文件大小、编码 CPU、全量与筛选查询时间、峰值 RSS，以及实际测试资源计量。
3. 逐局解码，避免一次性展开整个数据集；明确最大解压长度和错误处理。
4. 保留独立索引列、对局去重标识、匿名身份哈希及原始事实；记录编码和数据格式版本。
5. 校验每局内容往返一致，并比较所有聚合指标；仅比较总局数不足以证明正确。
6. 迁移过程保证新增写入不丢失；完成校验前保留可恢复副本。
7. 压缩后，Mod 使用计数等 JSON SQL 查询必须适配；不得漏掉这些读取路径。

后续若数据量扩大，应先改善重复构建和排序聚合对象的开销，再以更大、更丰富的实际样本复测。只有分析需求和性能数据支持时，才引入列式历史归档或更复杂的共享字典。
